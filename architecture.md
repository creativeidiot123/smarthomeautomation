# HomeDJ architecture

## Owners and truth

- **RemotePairingViewModel / RemotePairingCode**: the ViewModel owns only editable address/port/code drafts and scanner state, in memory across configuration recreation; process recreation restores confirmed credentials from RemotePrefs. Role changes discard drafts and invalidate outstanding scanner callbacks; duplicate scans and key replacement are first-wins. Scanning validates a bounded, versioned HomeDJ QR and populates the form, never connecting or saving by itself. Manual Pair validates private IPv4, the fixed port 47188 and code before calling RemoteControllerViewModel; its authenticated successful status reply remains the client save point. Invalid drafts leave an existing connection running. RemotePrefs remains the only durable credential owner, with a shared lock for server-key creation/replacement so concurrent service/UI startup cannot generate different keys. Legacy keys remain valid; only an explicit confirmed replacement while remote control is disabled revokes them. The server code/QR are hidden until revealed, reset on replacement, and never stored in instance state, logs or external services. New 26-character codes carry 128 random bits expanded to the existing AES key size; challenge/AAD/frame limits, listener, commands, playback and BLE key use remain unchanged.

- **ModeStore**: Preferences DataStore stores the device-local Server/Controller role.
- **PlaybackService**: one Media3 MediaLibraryService/session is the sole playback/queue owner, foreground only during supported media playback; observes the role to stop outside Server mode. `PlaybackPlayer` presents the active deck through Media3 1.8.1's ForwardingSimpleBasePlayer; two service-owned ExoPlayers permit the user-approved overlapping crossfade. `PlaybackRecovery` (Metrolist-style) keeps one failed track from halting the queue: network loss retries after 3/6/12 s, a CDN-rejected signed link is invalidated and retried once, anything else skips; five consecutive skips or the queue end stop playback.
- **ServerPlaybackViewModel**: client projection and commands to the same Media3 session, never another player. Android document-picker URIs are persisted when the user selects external audio.
- **RemoteServerService / RemoteChannel / RemotePrefs / RemoteControllerViewModel**: opt-in AES-GCM authenticated private-LAN protocol. The paired controller pages through server-owned playlists/tracks/downloads and sends verified track/playlist/download commands; it never accesses local audio or Google OAuth tokens directly. RemoteLibraryCommands validates catalog membership before Media3 mutation or WorkManager enqueue. `importPlaylist` sends only a link; Samsung parses it with YouTubePlaylistLinks, reads it through NativeAudioSource, re-checks the Server role and commits via SavedPlaylistStore. That reply can take seconds, so the controller sends it outside its command mutex with a longer read timeout and treats a timeout as an unknown outcome.
- **Remote listener lifetime**: after immediate foreground promotion, startup on Main observes the persisted role and remote opt-in before acquiring power, binding Media3 and opening the wildcard TCP listener; repeated starts do not acquire additional locks or launch additional listeners. The service owns a partial CPU wake lock for its opted-in lifetime, including music pauses, and a Wi-Fi high-performance lock only on Android <14. Destruction cancels its scope, releases power and closes sockets/futures; cancellation checked after socket publication closes the startup/destruction race. Sticky recreation revalidates role/opt-in. `RemoteServerRestoreReceiver` handles unlocked boot and app replacement with a finite broadcast-owned job, reads both existing owners, then requests the same foreground service; it never changes opt-in. Battery exemption belongs to Android, projected through the existing `PresenceViewModel` permission refresh and requested only by an Activity settings action. Samsung sleeping restrictions remain a separate manual setting; no accessibility/admin service, restart alarm or watchdog is used. Force-stop requires a user launch; no restoration of playback queues is added.
- **YouTubePlaylistRepository**: read-only Google YouTube Data API for owned/imported playlists, pagination and titles. Authentication token lives only in YouTubeViewModel, not in storage.
- **SavedPlaylistStore**: 4-MB atomic app-private JSON for account-scoped YouTube metadata; serializes screen/Worker writes in-process, erases metadata on explicit disconnect. Public links read without a token join the current snapshot as imported playlists; connecting a different account still replaces the snapshot.
- **NativeAudioSource / HomeDjMediaResolver**: NewPipe Extractor v0.26.5 with an application-owned HTTPS Downloader; Media3's ResolvingDataSource resolves stable internal video-ID URIs at load-time (prefer local file, else public non-DRM progressive audio) and caches transient signed links for at most four minutes per player-service instance; a YouTube refusal is cached for the same time so Media3 load retries do not re-query. Requests mirror NewPipe: the extractor Downloader sends NewPipe's desktop browser agent (extractor headers override; its consent cookie is forwarded, HTTP 429 maps to ReCaptchaException) and stream requests use NewPipe's YoutubeHttpDataSource shape (POST body, `rn` counter, visionOS or browser agent, web CORS headers). With no PoToken provider installed, visionOS-client links are preferred because ANDROID-client links can need one. It also reads public/unlisted playlists by ID (PlaylistInfo, bounded to `MAX_PLAYLIST_SONGS` = 2,000 songs and 25 pages; at about 100 songs a page this keeps a LAN link import usually inside the OnePlus's 45-s wait, and a timeout there is an unknown outcome the catalog revision later resolves) when no OAuth token is available. The extractor is initialized once, network reads run on Dispatchers.IO, extraction response bodies are size-bounded. Only HTTPS GoogleVideo audio URLs are accepted; no signed URLs are persisted.
- **OfflineAudioLibrary**: owner of app-private files in `files/offline_audio`, keyed by validated 11-character video IDs. WorkManager uses one unique job per ID for manual saves and a separate one for automatic playlist saves (so a withdrawn auto opt-in never swallows a manual save), each with its own atomic `.part` -> final file rename, at most four transfers at once in the process (WorkManager starts every queued save together, and unbounded blocking transfers starved the shared IO pool that DataStore needs, freezing the UI at start-up), no per-song or total-library size quota, and a device free-space check before each audio chunk (stop below 10 MiB free). `AudioTransfer` fetches 512-KiB Range requests (NewPipe downloader style) that must stay on the GoogleVideo CDN after redirects; a system interruption keeps the itag-keyed partial for a resumed worker, while a rejection or failed save deletes it. Completed files are durable. Each save request carries tags `homedj_offline` and `homedj_offline_id_<videoId>`; `pendingIds` reads queued/running saves from WorkManager (a projection) for live "Saving…" rows on both phones, while the committed file stays the "Saved" truth. Work queued before tags existed is not listed as saving until it finishes. An in-memory `revision` (starting at wall-clock time, like the catalog's) is bumped on `enqueue`, `cancel`, `remove` and after a worker stores the song's details; Samsung's `YouTubeViewModel` re-reads its Downloaded list on each bump and derives every "Downloaded" mark from it, and the status reply carries it as optional `downloads` so the Controller re-reads all loaded playlist or Downloaded rows when it moves (otherwise only rows still saving). A save that fails for good does not bump: Samsung's pending set and the Controller's saving-row poll already clear it. `DownloadNotice` owns Samsung's single silent download notification (channel `downloads`, id 43, low importance, not a foreground service): each worker updates it when it starts (skipped, without a WorkManager query, when the running count already lists its song) and when it ends without a retry (cancellation included, under `NonCancellable`), and `cancel`/`remove` update it with the stopped IDs. "N of M done" posts at most once a second because Android sheds a package's updates above about 5 a second; the first and the finished notice always post. `OfflineAudioLibrary.enqueue` returns false and queues nothing for a song that already has a file, so "Download the rest" on either phone queues only missing songs, and `download` returns an existing file before taking a transfer permit. Counts come from WorkManager's pending set per run (`DownloadRun`: songs seen pending since none were, which of them have a file); a run with songs left shows "N of M done" with a progress bar, a finished run shows how many were downloaded, and a run stopped with nothing saved removes it. In-memory only, so a process restart starts a new count. No notification permission is requested on Samsung; on Android 13+ it shows only once notifications are allowed. After a commit the worker writes the song's details and thumbnail through `OfflineSongInfo` (`files/offline_info`, `files/offline_art`, temp-and-rename, art HTTPS-only from `i.ytimg.com` without redirects, ≤1 MiB, best effort) so the Downloaded view works offline; details come from optional work input, else the catalog. `cancel` cancels both unique works per ID (a user-cancelled worker drops its partial via `stopReason`); `remove` cancels, then under `commitMutex` deletes audio, partials, details and art (the commit re-checks cancellation inside the lock); `removePlaylist` also takes the playlist out of auto-save so the next sync does not download it again. Playlist download state (`downloadState`) is derived from committed files and pending saves, never stored. Residual: a save whose cancel signal arrives after `remove` released the lock can still commit once.
- **Playlist play**: tapping a song in a playlist (Samsung Library, or LAN `playTrack` with the optional `playlist` field) queues that playlist from the song via `playlistQueue` (≤`MAX_PLAYLIST_SONGS` = 2,000 songs, always including the tapped one; the same bound caps LAN `playPlaylist` and scheduled slots); `UserCommandPlayer` starts the shuffle order at the tapped song and re-prepares an errored player on skip. LAN `tracks` items carry an optional `saving` flag; the controller re-reads only rows still saving on each poll. Older builds ignore both fields.
- **OfflineAudioWorker**: non-interactive, cancelable, idempotent per-song download. Checks Server role before and throughout the transfer, optional account key/playlist opt-in for automatic downloads, and network/space/size constraints; automated jobs require unmetered connection, manual jobs allow connected; reports failures by safe type and video ID, never signed URLs.
- **AutoLibraryConfig / AutoLibraryWorker**: device-local auto-save settings and the unique inexact hourly WorkManager job `homedj_playlist_sync` (unmetered + battery-not-low), scheduled whenever Samsung's screen opens in Server mode, whether or not auto-save is on; `ExistingPeriodicWorkPolicy.UPDATE` moves a job left by an older 12-hour build to the hourly period. Each pass re-checks the role, takes a silent Google token (`silentYouTubeAccess`, memory only) only for the snapshot's own account, refreshes that account's playlist list, then refreshes up to 30 saved playlists through `PlaylistRefresh` and, with auto-save on, queues whole auto-save playlists as account saves (skipping songs already pending), up to 150 new saves per pass in total. No Termux command or other-process service lifetime.
- **PlaylistDownloads / PlaylistDownloadWorker**: whole-playlist downloads past one batch. "Download"/"Download the rest" on Samsung and the LAN `savePlaylist` queue up to 250 missing songs (failed ones again, already pending ones not twice) as manual saves and, before queuing even a single batch, synchronously commit the requested playlist in SharedPreferences `homedj_playlist_downloads`. Each save that ends without a retry enqueues the unique one-time `homedj_playlist_topup` (KEEP), which re-checks the Server role and refills the queue to 250 pending saves with songs not downloaded, pending or failed (`OfflineAudioLibrary.failedIds`, WorkManager FAILED work); a playlist with nothing left to queue is forgotten, and the hourly sync tops up as a safety net. `cancel`/`remove` forget every waiting playlist listing a stopped song first, so a top-up never undoes a stop. Each save skips WorkManager retries (`OfflineAudioLibrary.MAX_RETRIES = 0`), including `BotCheckException` (bot check, reCAPTCHA: an address rate limit) and timeouts; work already queued by older builds uses the same policy on its next attempt. Failed songs are excluded from top-ups; an explicit download can try them again. **DownloadBackup** owns the fallbacks instead. In the attempt, `OfflineAudioLibrary.transfer` follows `DownloadBackup.step` on non-rejection `IOException`s: resume the same link and kept partial immediately while failures in a row stay under `MAX_RESUMES` (3; new bytes reset the count; a 4xx `AudioHttpStatus` is never resumed), then re-extract once (role/consent re-checked first), then move to the next of at most `NativeAudioSource.MAX_FALLBACK_STREAMS` (3) ranked streams (`resolveAll`; playback still takes only the first), then give up; `DownloadRejected`, cancellation and extraction refusals end it as before, so the loop is bounded. Each step logs one safe line (step plus failure code). Later, a manual, non-backup save whose final failure `laterMayHelp` (bot check, network, extractor, HTTP; not `TrackUnavailableException` or `DownloadRejected`) is added under a process mutex to SharedPreferences `homedj_download_backup` key `later` (at most `MAX_PLAYLIST_SONGS` IDs). `AutoLibraryWorker` calls `requeue` with its remaining pass budget: in Server mode it forgets the taken IDs first (an interruption loses a backup rather than repeating one), then enqueues the not-pending ones as manual saves with optional input `backup = true` and an unmetered constraint; a backup that fails is not remembered again. Automatic saves are excluded because the sync re-queues missing auto-save songs every pass. `cancel`/`remove` call `forget`, so the pass never undoes a stop. Until the pass runs the song still shows "Download failed". **SongSubstitute** sits in front of resolution for downloads only: `OfflineAudioLibrary.download` takes the worker's `YouTubeTrack` (work input, else catalog) and resolves through `SongSubstitute.resolver`. When resolving the song throws `TrackUnavailableException` other than `BotCheckException`, it runs one `NativeAudioSource.searchVideos` (regular YouTube `videos` filter, no Shorts/live, ReCaptcha mapped to `BotCheckException`, other extraction errors to an `IOException` the later pass may retry) and tries up to 3 `pick`ed uploads: not the same ID, not a "- Topic" channel, all title words, length within `toleranceSeconds`, no unrequested version words, artist-named then closest length first. The first that resolves is kept for the attempt (link refreshes reuse it) and saved as `<originalId>.<ext>` with the original song's details and art, so every owner keyed by video ID is unchanged; one safe log line names both IDs. No match rethrows the original refusal. Playback streaming still uses only the song's own video, so a refused, not-downloaded song is skipped as before. Failed songs show "Download failed" on Samsung and, via the optional `failed` field of `tracks` rows, on the OnePlus. No second extractor: yt-dlp was considered and declined (bundled Python and a JS runtime, a process this repo does not run, and the same address-wide bot block).
- **PlaylistRefresh**: owner of re-reading one saved playlist (API with the snapshot account's token, or as a link through NativeAudioSource when there is none or the API refuses) for the hourly job, Refresh on Samsung's playlist page, the first Samsung open of an uncached playlist while signed in, and the optional LAN `refreshPlaylist` command (`id`; reply `message` plus optional `added`/`queued`; an older Samsung answers "Unknown command" and the OnePlus asks for an update). It commits via `SavedPlaylistStore.refreshTracks` only to the snapshot it read (same owner, playlist still listed) and only after re-checking the Server role. Songs removed upstream leave the list but their audio stays. Songs new since the last stored list (a first read has no baseline) are queued with `playlistId` and no account (manual work name, Wi-Fi-only via `networkForDownload`) only when one of the playlist's previous songs is downloaded or pending. Concurrent refreshes may queue the same songs, which unique save work keeps to one download.
- **LiveAudioCastService / LiveAudioSink**: user-consented MediaProjection and AudioRecord playback capture on Controller sends fixed 48-kHz stereo 16-bit PCM packets (10 ms; Samsung accepts any aligned packet up to 20 ms, so mixed builds interoperate) through the existing authenticated AES-GCM TCP session; Samsung's RemoteServerService accepts one live cast, pauses Media3, and feeds an AudioTrack with focus and the low-latency performance mode and an explicit 50 ms Android start threshold (API 31+; API 29/30 reduce the effective buffer instead). The sink keeps an adaptive queue target (memory only, per cast): 50 ms on good Wi-Fi, +20 ms after each AudioTrack underrun up to 250 ms, -10 ms after 20 s without one (`SystemClock.elapsedRealtime`); once more than target + 40 ms is queued it drops packets until the target remains, so a burst after a Wi-Fi stall becomes a short gap instead of lasting delay (live audio prefers gaps over latency). The OnePlus bounds stale audio at the sender too: 100 ms of capture buffer and a fixed 16 KB socket send buffer (no autotuning). Each PCM frame's AES-GCM AAD includes its sequence number, so replayed, dropped or reordered frames end the cast (both phones need the same build). Multiple short-lived remote sessions are handled concurrently with a six-connection semaphore. Live PCM is never persisted. After Samsung accepts the stream and the first capture read succeeds, LiveAudioCastService sets OnePlus STREAM_MUSIC volume to zero once per cast; later manual changes and the volume on stop are left alone. Volume remains Android-owned, with no saved app setting or LAN change. Stopping the service, permission revocation, remote playback or network interruption closes the live socket and releases the capture/sink. Samsung ends a cast before play/pause and skips, but for a song or playlist only after `RemoteLibraryCommands` accepted it (`endsCast`); the OnePlus stops its own cast before sending such a command and marks the stop synchronously, so the expected socket close is not reported as a Wi-Fi failure. No additional publicly exposed listener or pairing secret.
- **RemoteActivity** (process `object`, Samsung): in-memory, newest-first feed (30 entries) of changes made from either phone (OnePlus commands recorded by `RemoteServerService.handle` after they apply; Samsung UI actions by its ViewModels, custom session commands only on success). Display only, never a command queue; lost with the process; titles only, never links/tokens/addresses, not logged. Samsung shows it as the Activity card, and every status reply carries the newest 8 as optional `activity` (age in seconds, so phone clocks may differ) for the OnePlus card. Race protection: the OnePlus sends the state it showed (`playPause.play`, `shuffle.on`, `next/previous.index`), so Samsung applies intent instead of toggling stale state and refuses a skip of a song it already left; older builds ignore these fields and toggle. `SavedPlaylistStore.revision` (bumped per commit, wall-clock seeded) reloads Samsung's Library screen and is sent as optional `library` so the OnePlus re-reads its playlist list.
- **HomeDjActivity / YouTubeSection / YouTubeViewModel**: user actions, UI state and read-only projections. No Connect YouTube control or prompt exists on either phone; the Activity still tries silent Google authorization on Server start, and only an account granted by an earlier build shows the Settings YouTube card (Sync, auto-save switch, Disconnect) and the per-playlist auto-save chip. On-demand stream resolves are Activity-lifecycle-bound; durable downloads belong to WorkManager rather than the UI lifecycle.
- **PlaylistSorting / PlaylistPage / PlaylistSortStore / PlaylistSortViewModel**: song sorting is a view-only projection shared by both phones and Downloaded pages. `PlaylistSortStore` owns one `playlist_sort:<playlist ID>` string per playlist (Downloaded pages use `DOWNLOADED_SORT_KEY`) in the existing `homedj_settings` DataStore; values are `PlaylistSort.name`, playlist order stores nothing, and missing/unknown values mean playlist order. The Activity's `PlaylistSortViewModel` reads it once, survives recreation, queues writes in tap order under a mutex and publishes each selection after DataStore commits. Storage failures retain the previous selection and show a safe error. Each phone keeps each playlist's own choice across visits, tabs and app restarts; keys of removed playlists stay until app data is cleared (a few bytes each); it is not account-scoped and stays on disconnect or role change until changed again or app data is cleared. Title/artist sorts ignore case, unknown artist/length sorts last, and ties keep source order. Search and sorting cover every locally available song. PlaylistPage uses a bounded-height LazyColumn with stable per-occurrence video keys, including repeated songs, and no 100-row display cap; ScreenFrame disables its outer scroll for playlist/Downloaded pages. Both phones render one complete list (up to 5,000 cached rows on the Controller); a complete cached list stays visible until its complete replacement is ready. There are no load-more controls or partial-list sorting. Stable song projections keep sorting from repeating on unrelated playback updates. Sorting never writes playlist metadata, changes the Media3 queue or sends a LAN command; song actions retain their original IDs.
- **HomeDjScreens / RemoteUiSection / YouTubeSection / ControllerLibrary / PlaylistPage**: Material 3 Expressive presentation groups each role into Home (playlist grid, playlist page, Downloaded page), Schedule, Lights and Settings behind a bottom navigation bar. Tab choice, the open Home page and search text are restorable Compose-only UI state; remote and playback truth continue to come exclusively from their ViewModels/services. Removing downloads always asks first in a dialog that only a button closes. On the OnePlus every page is a live or explicitly cached Samsung projection and every download change is a `cancelSave`/`removeSaved` command Samsung validates against its own catalog (`RemoteLibraryCommands.changeDownload`); `withSavesQueued` shows a confirmed change until the next refresh. Pairing codes are masked until revealed in Settings. Wallpaper-based Material You colors apply where Android supports dynamic color.
- **PlayerUi / MusicListItems / MusicArtwork** (stateless Compose): `MusicShell` hosts the mini player and the full-screen player (open/closed is `rememberSaveable`; system back, the chevron, or a downward drag closes it; it closes when the queue ends). Both render `NowPlayingUi`, a per-role projection of `ServerPlaybackUiState` (Samsung) or `RemoteUiState` (OnePlus). Position is a snapshot (`positionMs` at `positionAt`, `elapsedRealtime`) that the seek bar extrapolates while playing; a seek is sent once on release (Samsung `MediaController.seekTo`, OnePlus LAN `seek` with the shown song index, refused by `seekTarget` if Samsung already left that song). Song menus are dropdowns on ⋮ or long press. Artwork: `youTubeArtworkUrl` derives an `i.ytimg.com` URL from a validated video ID; the one item builder `youTubeMediaItem` (used by `ServerPlaybackViewModel`, `MusicScheduler`, `RemoteLibraryCommands`) sets title, artist and `artworkUri`, so the session notification also gets art and the Samsung UI reads it back from the controller timeline. Coil's singleton image loader owns the memory/disk image cache, configured by `MusicImageLoader` below; it holds only public thumbnails and is not cleared on YouTube disconnect.

- **MusicImageLoader**: `HomeDjActivity.onCreate` configures Coil's singleton before composing either role's UI. It keeps Coil's bounded memory cache and uses `files/artwork_cache` for persistent public thumbnail bytes, keyed by the full URL (sizes remain separate), with a 128-MiB LRU target. Coil owns serialized edits per key, atomic commits, incomplete-write cleanup and background eviction. A successful cached response is reused without a network freshness check, matching Coil 3.3.0's default strategy; changed URLs, eviction, or app-data removal cause a new fetch. The cache is device-local, contains no account credentials, survives ordinary system cache cleanup and is retained on disconnect. After an opened playlist loads, its ViewModel prefetches public thumbnails through Coil 3.3.0 with two cancellable disk-only requests, using BlackholeDecoder to skip bitmap decoding. Navigation/reconnection/stop cancels the Controller browse job and its prefetch; Samsung selection changes cancel its track job. Prefetch does not keep the whole library in bitmap memory. The former disposable `cacheDir` image cache is left for Android to reclaim; downloaded-song art remains separately owned by `OfflineSongInfo`.

- **Playlist browsing cache**: Samsung opens already-stored tracks through `cachedPlaylistTracks`, scoped to the signed-in account; explicit Refresh and the existing hourly worker refresh them. Store revisions also update the selected track projection. An absent snapshot is fetched on first open; an empty stored playlist is a valid cache hit. OnePlus uses a ViewModel-owned `RemoteBrowseCache` (`files/remote_browse_cache.json`, version 1, atomic replace, at most 4 MB, evicting other cached pages to fit). It stores only complete playlist/catalog/Downloaded metadata, original order and a SHA-256 peer binding of address plus pairing code; addresses, keys, OAuth and live download flags are omitted. Cached download marks/counts are unknown until Samsung replies. The owner keeps one typed memory cache backed by the existing file, with IO and one mutex. A known unchanged catalog revision reuses catalog metadata; playlist/Downloaded lists also require the same known downloads revision and no pending songs. Restored metadata omits live download flags and re-reads them once online. Pull-to-refresh, retry, import and playlist refresh force a read. Confirmed save/cancel/remove commands invalidate in-memory download confirmations and wake the status poll while retaining cached metadata. Initial transfers use the existing commands and fields, packing up to 60,000 UTF-8 JSON bytes per reply so it fits the 64-KiB encrypted-frame limit older builds keep (the limit is now 128 KiB, raised for worst-case Lights replies); most ordinary playlists fit in one reply. Larger lists and older 40-row servers are assembled privately before publication. Missing/no-progress chunks, changed totals and more than 5,000 rows fail safely with retry. Samsung derives download marks from one scan of committed audio filenames, using the same filter as its Downloaded view. A changed peer or known catalog revision invalidates cached lists; unknown-revision peers revalidate on every visit. Startup restores the cached catalog before connecting, and cached cards remain browsable offline with playback disabled and a cached label. Revision changes re-read the current browser section; generation checks and cancellation prevent obsolete results from publishing. This is disposable metadata only; server playback/download authority, old persisted keys, and LAN fields remain unchanged.

## Lights

- **House rules** (`HouseScript` / `HouseRules` / `HouseRulesRunner` / `BulbWatch`): Samsung's `HouseRules` owns the rule text (SharedPreferences `homedj_house_rules`, `script`, ≤4000 chars) behind its own mutex. A save is accepted only in Server role, when `HouseScript.parse` succeeds and every referenced light/group/scene/schedule name exists now; names are not IDs, so the runner resolves them again at run time and a renamed or removed item is skipped with an Activity line. The OnePlus edits through the additive LAN `houseRules`/`houseRulesSave` (reply carries `script`; an older Samsung answers Unknown command). Both phones' `HouseRulesViewModel` saves first-wins; the editor draft is Compose-only until Save. `HouseRulesRunner` runs on Main inside `RemoteServerService` (its wake lock and Media3 controller) and ends with it: every 6 s, while Samsung is on Wi-Fi, it reads General Diagnostics RebootCount/UpTime (endpoint 0, cluster 0x33) from each light a rule watches through `MatterLights.boot` (3 s answer budget counted after the controller lock, so queueing behind pairing or commands is never an outage). The loop ticks every 0.5 s (0.25 s while a watched light is dark). A light with a trusted ping is pinged every tick (`InetAddress.isReachable`, 400 ms, unprivileged ICMP with TCP-echo fallback): lit and silent asks Matter at once (retiring the session the bulb lost while it boots), dark and answering asks Matter at once, lit and answering asks Matter every 6 s (for flicks no ping can miss), dark and silent never asks Matter, because a Matter handshake sent to a dark bulb hangs ~11 s in the SDK (no timeout/cancel API) and delays its return. A ping is trusted per light only after its current session address (`MatterLights.address`, `getIpAddress`) answered while the light was up, re-learned after each return; otherwise the 6 s Matter asks stay. Addresses are memory only and never logged. The first missed ping starts the outage (plain `turned off` = 2 s, at least 8 missed pings); the lost Matter session is retired by one background ask once per outage, after any `turned off` hold of 3 s or less has fired, and lit lights' routine Matter asks pause while another watched light is dark, so nothing queues on the one Matter controller in front of that light's steps. The dark set is also published each tick as the memory-only companion projection `HouseRulesRunner.dark` (empty once the runner ends), which scenes and previews skip. Steps skip watched lights that are dark (a command to an unpowered bulb would wait up to 20 s and hold back every later step, e.g. `music off`). `starts` lines are written to the bulb's StartUpOnOff in the background while it is lit, once per service life per value, retried at most once a minute; removing the line leaves the bulb's setting as it is (`starts as before` restores the Matter default). A seen switch that no rule takes (time window, length) is recorded in the Activity feed. `BulbWatchPolicy` (pure, memory-only per service life) turns polls into `turned off` (each `for` hold once per outage), `turned on` (power back: new boot, or any answer after a hold fired; and each `turned on for` hold once), `off and on` (new boot; outage length) and `on and off` (outage confirmed for 10 s after a return; on-time). An answer without a new boot or fired hold is a blip; Samsung leaving Wi-Fi restarts the outage clock. On power back the runner reads the bulb (`Lights.readLight`) before rules run; `was` checks use the recorded brightness from before the switch, `is` checks the record when the rule starts (off/unknown = 0%, on at unknown level = 100%); all checks of a rule are decided before its first step. `+N%`/`-N%` move each target light from its record within 1–100% (off lights only brighten) as individual changes. Steps go through the existing `Lights` owner (`change`, `changeGroup`, `applyScene`, `lightsRuleEnabled` via `editExperience`, `followSchedules`), so role checks, preferences and history stay there. `schedules now` (`LightExperience.latest`) re-runs, oldest first and without rule fades, only the enabled schedules whose last occurrence in the past day is still the latest for some light, ignoring the re-enable/save start boundary (which only stops alarm catch-up), so `schedules on` then `schedules now` works. `music off` pauses through the service's controller and remembers the media ID in memory; `music on` resumes only that song if nobody pressed play or changed it (`PresencePolicy.samsungShouldResume`), never while casting. Limits: polling cannot see a switch flipped back faster than the bulb boots, a long bulb/router Wi-Fi outage looks like `turned off`, and a quick `off and on` also counts as `turned on`. Two-phone and real-bulb behavior is not verified by JVM tests.

- **Remote light setup**: `RemoteLightSetup` validates and bounds the three additive setup commands and maps their safe outcomes; it holds no device state. OnePlus's `LightsViewModel` sends explicitly confirmed setup/forget actions through `RemoteChannel`, and renders the snapshot/capability returned by Samsung. `Lights.handleRemote` routes to the same `Lights.pair`/`forget` owner and Samsung's `MatterLights.discover`; the existing enabled/role gate, owner mutex and sole Matter controller remain authoritative. Codes stay in request memory and never enter the snapshot, logs or persistence. The Controller requires the optional `lightsSetup` capability; no unsupported setup is offered against older Samsung builds. Pair/forget disconnections refresh server truth without resending the mutation. Contract: [docs/controller-light-setup.md](docs/controller-light-setup.md).

- **Scenes, scheduling and controls**: `Lights` owns the optional `experience` record in the same mutex/SharedPreferences commit as bulbs and automation. `LightExperience` supplies scene/rule validation, independent rule edits, feature preservation for legacy Controllers, bounded history and fresh-Home conditions; `LightExperienceCodec` shares additive bounded disk/LAN JSON. The UI and `LightsViewModel` emit individual edits, never replace unrelated rules. A new/edited/re-enabled rule gets a server-owned `activeAfter` boundary; creating the first rule initializes the run checkpoint, and subsequent edits preserve due work. Solar times use local NOAA equations and Samsung's time zone; absent events are rechecked at the next midnight through the existing alarm. Scenes (applied or scheduled) and the editor's preview/restore send to all their lights at once through `MatterLights.sendEach`, each light within 6 s: one commit records every light's individual intent first, one commit afterwards records the lights that acknowledged (also when cancelled), and a light that fails or times out keeps its record and counts against the outcome. Lights the house-rules watch currently sees unpowered (`HouseRulesRunner.dark`) are skipped. Only-if-Home consumes `PresenceWatch`'s fresh authenticated Home-vote projection (`OnePlusSeen.confirmedHomeAt`), never BLE alone; listener off, unknown or stale votes skip with a recorded result. Native fades pass transition tenths in existing Matter commands, including level zero for fading off. `MatterLightReading` performs one explicit SDK read with a bounded deadline; `Lights` commits the observation without changing preferences, and no subscription or polling owner is added. UI-local tabs/drafts remain saveable primitives, and the old inline control/schedule editor path is replaced. Full contract: [docs/lights-experience.md](docs/lights-experience.md).

- **Juggle**: a scene with variation on and a juggle interval (`LightScene.juggle`) makes its lights the single `LightsVariation.juggle` group when applied (`LightJuggles.applyScene`); any newer per-light or all-light variation edit, another scene for those lights, or forgetting a light removes them (the group ends below two). Juggling lights always also have their own variation entry, which carries the compact `j` mark. `LightVariationRunner` keeps the swap assignment in memory only: each interval it reshuffles the lit, coloured, varying members (`LightJuggles.shuffle`, every light moves) and steps them at once; `Lights.vary` receives only the assigned source light and reads its recorded colour under the owner mutex (`LightVariations.next`), so a scene applied while the runner waited is never overwritten by an older colour; it plans the variation step around that colour (`LightVariations.plan(juggled, sendColor)`), sends the colour even with hue/saturation variation off, and sends each light's own colour back once it stops juggling. Nothing is committed; a listener restart starts from each light's own colour, and restores always go to the record.
- **Scene editor preview**: `LightScenePreview` (Main-confined in `LightsViewModel`, reset on role change) records bulb states when a scene editor opens, sends only bulbs whose target differs from what they last showed (computed at send time through the latest-wins `LightLiveSender` key, so a replaced queued send loses nothing), restores unticked bulbs and, when the editor leaves composition (not on configuration change), every previewed bulb; it forgets the start states only after restores drained. Unconfirmed sends become unknown and are resent. `Lights.preview` sends the changes as given and commits only bulb state, so preview + restore leave preferences, groups, presence and variation intent untouched; the OnePlus uses `lightsPreview`. First-wins Lights operations now wait for queued live sends instead of being dropped, so Save lands after the last preview. Lights still showing the preview when the process dies are not restored.
- **Light variation**: `Lights` owns `LightsVariation` (all-light value plus per-bulb overrides) and scene `variation`/per-light `variations` in the same mutex/commit as the rest of the record; `LightVariations` holds the pure step/restore/edit rules and `LightVariationCodec` the bounded integer JSON (6-bit legacy value under each key plus an optional full `<key>2`; reads prefer `<key>2`). Latest change wins: the all-light value clears per-light overrides; applying a scene (including scheduled) writes its lights' overrides; a scene from an older build (null) leaves variation alone, and older Controllers' scene saves preserve it. `LightVariationRunner` is launched in `RemoteServerService`'s `SupervisorJob` scope, so it lives exactly as long as the opted-in Server listener and its locks. It keeps per-bulb next-step times, drift offsets (`VariationDrift`, so each step walks on from the last), the varied set and failure counts in memory only, suspends on `Lights.state` while no lit bulb has variation on, and wakes early on setting changes. Every step goes through `Lights.vary` under the owner mutex (role re-check, fade hold recorded by `apply`), computes the next drift step around the current record and sends it through `MatterLights.send` with a 6 s limit; it never commits, so the screen and snapshot keep showing base settings and a later direct change becomes the new base. Steps use commands that cannot power a bulb on; a bulb that stops varying gets one restore with ExecuteIfOff. Not restored when the listener stops (lights hold their last step), and Check light records whatever the bulb reports. Groups carry their own optional `LightsGroup.variation` in the same configuration record; `variationOf` resolves light, then group, then all lights at every read (runner, juggle, UI), so membership changes need no copy. Only `LightVariations.edit` (`lightsGroupVariation`) changes it; `Lights.saveGroup` keeps the stored value and clears added members' own variation; deleting a group removes it with the group.
- **Light show**: `Lights` owns the `LightDance` intent in the same record and mutex (`LightDances.edit` via `lightsDance`). `MusicPulse` is a process `object` holding one `Deck` per player deck's `PulseAudioSink`; each deck's `BeatTracker` and clock run only on that deck's playback thread and publish immutable `PulseReading`/`DeckClock` snapshots through volatile fields (no PCM leaves the tracker's 6 s onset envelope; nothing persisted, logged or sent). `MusicPulse.now` picks the loudest playing deck with a fresh clock, so the incoming deck wins once a crossfade passes halfway; `MusicNow` maps the grid from media time to elapsed realtime with playback speed. `LightDanceRunner` is launched beside `LightVariationRunner` in `RemoteServerService`'s scope; it keeps beat count, pending cues, answer-time estimate, failure backoff and the artwork palette in memory only, plans one beat at a time with pure `LightDances.beat` (latest grid wins; late cues dropped, never queued), and sends every cue through `Lights.dance` under the owner mutex (role re-check, fit re-checked against the current record so an off light is skipped, 1.5 s Matter limit). `Lights.dance` extends the variation hold (`fadeHolds`) so `Lights.vary` leaves dancing lights alone; nothing is committed, and lights that stop dancing get one `LightVariations.restore`. The live status is the runner's companion `StateFlow` projection, shown on Samsung and copied into LAN replies as fixed text.
- **Groups/preferences extension**: `Lights` also owns `LightsConfiguration` in the same SharedPreferences commit and mutex as bulbs/automation. `LightsGroups` resolves per-field individual overrides, latest-change-wins rejoining (`rejoin`: a group command, group rule or joining a group clears its members' individual power/brightness/colour, and an all-light command or rule (`allChanged`) clears every bulb's and merges its fields into every group's remembered defaults, keeping presence flags), group presence inheritance, membership validation and dynamic group schedule targets; `LightsGroupsCodec` handles optional bounded configuration JSON. A bulb has at most one group. Group commands and individual intents are saved separately from last acknowledged bulb state, so unreachable bulbs retain their previous observed state and failure stays visible. Disk commit failure throws before publication. Joining an existing group clears the added bulbs' individual power/brightness/colour and applies the group's saved defaults to them. Clearing preferences immediately applies available group defaults; absent defaults leave current bulb state alone. Group deletion removes only its rules, confirmed in the editor; forgetting a bulb removes its membership/preferences without turning an empty group rule into an all-light rule.
- **Rule precedence**: rules remain at most once and bounded by the existing late window. At one occurrence, all-light rules run before group rules, then selected-bulb rules. Selected-bulb rules save individual overrides; a later group command or rule clears them for its members, and a later all-light command or rule clears them for every bulb. Group rule `groupId` follows membership at execution; `bulbs` is retained for older readers. Old Controller automation edits preserve group targets under the owner mutex; new clients send optional `groupsVersion = 1` so explicitly changing a rule's target still works. Presence chooses individual nullable flag, group nullable flag, then existing global flag; its temporary off/restore does not replace saved light preferences and restores only the existing presence-off set.
- **Discovery/QR**: `LightsViewModel` starts a single bounded Samsung-side discovery from either phone through `MatterLights`, using the sole controller and SDK browser's own timeout/cleanup. `stopDnssd` is deliberately unused because it stops operational advertising, not the browse. Results are transient safe names/discriminators, never addresses or credentials. `HomeDjActivity` hosts Google code-scanner UI; its completion listeners capture only the ViewModel so the scanner's Activity stop/recreation does not drop a result or retain the host. The ViewModel guards duplicate scanner launches, validates the code and optional selected discriminator, and requires a separate pairing tap. Scanner failures preserve manual entry. Setup codes and camera frames are never saved. On Samsung, `HomeDjActivity` hosts the Bluetooth permission request for new-bulb setup; `LightsViewModel` owns `bluetoothReady` and re-checks the grant, Bluetooth being on, and `validLightWifi` at pairing time. The Wi-Fi password lives only in `LightsViewModel` memory (cleared on role change), the Add-light composition (`remember`, not saved state) and that pairing call; `Lights.pair` validates it again as the owner and, on success only, stores the Wi-Fi name (`wifi_name` in `homedj_lights`) for prefill. For OnePlus setup, only the code is sent temporarily over the existing authenticated encrypted LAN connection to Samsung; camera frames and fabric credentials never cross that connection. Group/preferences dialogs render the same Samsung snapshot on both phones; no second store/controller or background owner is introduced.

- **MatterLights** (Samsung process `object`): the only Matter controller (connectedhomeip `ChipDeviceController` + `AndroidChipPlatform`), created once on `Dispatchers.IO` on first use and kept for the process. A `Mutex` makes pairing, commands and forget one at a time; within it `sendEach` (pure `acknowledgedEach`) sends one batch to several lights concurrently, each on its own session with its own timeout (connectedhomeip v1.6.1.0 allocates a native callback per connect/invoke and takes its stack lock per call), so an unreachable light costs only its own limit; native callbacks resume `suspendCancellableCoroutine`s, a cancelled connect releases its device pointer, and each command batch releases it in `finally`. Pairing is on-network with a share code, or, when Samsung's Add-light passes `LightWifi` for a new bulb, also over BLE with those Wi-Fi credentials handed to the SDK for that one call (120 s timeout, `stopDevicePairing` on failure) and returns the node ID; its own deadline becomes a `TimeoutException` so the ViewModel replaces progress with sharing/Wi-Fi guidance, while owner cancellation still propagates. `forget` asks the bulb to remove HomeDJ's fabric. It stores nothing itself. Command bytes come from pure `LightCommands` (setup-code check digit, colour/level ranges, TLV).
- **Lights** (Samsung process `object`): the single owner of the paired bulbs, their last acknowledged state, the automation and the presence-off set (SharedPreferences `homedj_lights`, one edit per commit, migrating the legacy `node_id` on first load). Every mutation takes its `Mutex` and re-checks the Server role. A pairing is recorded only after commissioning succeeds. A change goes to the bulbs one after another, and each bulb's record updates only after it acknowledged (colour first with ExecuteIfOff, then level or power; a bulb not recorded on gets level or power first, because some bulbs drop a colour sent while off), so a failed bulb keeps its old record. `forget` drops the bulb even if it does not answer. A bulb's optional `permanentlyOff` flag (bulbs JSON, written only when true; additive LAN `lightsPermanentlyOff` {id, off} with reply capability `lightsPermanentlyOff`, which the OnePlus needs before it shows the switch) is user intent kept on the bulb record: setting it sends nothing, and while it is set `Lights` sends that bulb nothing. Direct controls and Check light are refused with a fixed message; all-light, group, preference, presence and schedule changes skip it and count it as done; scenes and previews leave it out of their sends and counts (`LightExperience.sceneTargets`); variation and light-show steps skip it; house rules' `starts` writes skip it. Only reading its boot identity for the switch watch continues. A command that timed out has an unknown outcome; the screen shows the failure. Pure rules and JSON live in `LightsModel` (`LightsPolicy`, `LightsCodec`). The LAN `lights*` commands reach it through `handleRemote`, checked before playback readiness in `RemoteServerService.handle`.
- **LightsWork / LightsAlarmReceiver / LightsWorker**: a rule alarm, boot, update or clock change enqueues `homedj_lights_rules`; `PresenceWatch` enqueues `homedj_lights_presence` once per absence (the same 5-min rule as music auto-pause, independent of it) and on the next home check-in. `Lights.runRules` records the run time before applying, so it is at most once. It applies the rules due in (last run, now], oldest first, and skips rules more than 15 min late. Then it re-arms the next one, or cancels the alarm outside Server role. Legacy whole-automation saves reset the run time; new per-rule edits use an activeAfter boundary and preserve other due rules, while all edits re-arm; opening the Lights tab in Server mode also enqueues a rules pass, which re-arms after a role change. Workers never retry.
- **LightsViewModel / LightsSection / LightsAutomationSection**: one Lights tab on both phones. On the Samsung it projects `Lights.state` and calls the owner. On the OnePlus it fetches Samsung's snapshot when the tab opens, after every command (each reply carries it) and on retry; there is no polling, so automation changes show at the next fetch. Taps are first-wins, messages are fixed and safe, and failures are logged by type and Matter error code only. A LAN timeout counts as an unknown outcome and triggers a refresh. Direct light changes (power, swatches, brightness bars and colour sliders in `LightControls`) are live: each step is offered to `LightLiveSender`, which keeps one send in flight and only the newest value per target and field queued (re-queued in last-touched order), so the bulb follows the finger and ends on the released value; they never mark the screen busy and are ignored while a first-wins operation runs. Owner state arriving while a newer value is queued is held and shown once the burst settles; controls keep the dragged value while the finger is down. A live LAN timeout is an unknown outcome shown as a message, without a resend. Power commands and their bulb-native on/off transition are unchanged. Group and all-light tiles show values derived from member bulbs, never a stored copy.

- **Matter pairing lifetime and attestation handoff**: each in-flight pairing has separate completion and attestation signals. The native attestation callback only completes the pointer signal because connectedhomeip v1.6.1.0 holds its stack lock during that callback. `awaitMatterPairing` owns native startup, the attestation wait/continuation and failure/cancellation cleanup on `Dispatchers.IO` within the existing mutex. The native `stopDevicePairing` call can wait for that lock and must never run on Main, which also serves LAN commands. The coroutine selects completion or attestation, invokes `continueCommissioning` once outside the callback, then awaits final commissioning. Nonzero SDK result, timeout, startup failure or cancellation stops the attempt once; success does not stop it. When the SDK's own ~30 s `SetUpCodePairer` search (BLE/DNS-SD) ends with nothing left to try, v1.6.1.0 reports it only as `onStatusUpdate(SecurePairingFailed = 1)`: `OnSessionEstablishmentError` skips `onPairingComplete` when no PASE device exists. That status completes the result as a `TimeoutException` (first-wins), so the existing timeout/Bluetooth messages show then; the 120 s deadline remains the backstop. No process-owned coroutine or posted pointer survives the attempt. The existing attestation acceptance policy is unchanged.

## Home detection

- **PresenceService** (OnePlus, Controller mode only): one foreground service while `PresenceStore.enabled`; owns the Home/Away verdict, a 2-of-3 vote of Wi-Fi reachability, Samsung's beacon and the geofence (`PresencePolicy.homeSignals`/`next`, `elapsedRealtime` times), as an in-memory projection (`PresenceService.state`). One loop on Main does everything serially; the Wi-Fi network callback, the beacon and `onStartCommand` only wake it through a conflated channel. Its `presence` request (carrying `autoPause` and the current `home` vote, re-sent at once when the vote changes) is both the Wi-Fi probe and Samsung's check-in; any authenticated reply (including `Unknown command` from an older Samsung) proves reachability. It advertises this phone's beacon only while Home, so the static ID is not broadcast away from home. Role and opt-in are re-checked from `ModeStore`; START_STICKY, boot/update and geofence broadcasts (`PresenceReceiver`, not exported) restart it, the last being allowed to start a foreground service from the background on Android 12+.
- **PresenceStore** (OnePlus SharedPreferences `homedj_presence`): opt-in, `autoPause`, home centre (never sent, never logged) and the last geofence transition written by `PresenceReceiver`. `PresenceGeofence` registers one fence with an enter/exit initial trigger on each service start, retries at most every 15 min while the state is unknown (boot, location off), and is removed when detection is turned off.
- **PresenceBeacon**: per-service BLE owner. Advertises an 8-byte HMAC-SHA256 of the pairing key per role under HomeDJ's own 128-bit service UUID, and runs one filtered low-power scan for the peer (batched when the chip supports it). `update` reconciles idempotently each tick; Bluetooth off, missing permission or a pairing change stops it; a refused start waits 5 min.
- **PresenceWatch** (Samsung, owned by RemoteServerService on Main, memory only): starts its beacon after the first check-in in the service's life. Seen = OnePlus beacon or check-in. Pauses once per absence (5 min unseen, `autoPause` on, playing, not casting) and records it in the Activity feed; resumes only on an authenticated check-in whose `home` vote is true, only the paused song and only if nobody pressed play, so a replayed beacon can delay a pause but never start music. With an arrival playlist set (`LightsAutomation.homePlaylist`) it does not resume; `Lights.presence(home)` (via `LightsWorker`) applies `homeScene` instead of restoring and asks `MusicScheduler.PLAY_SCENE` with `ifIdle`, which refuses while anything plays, under a new key per arrival so the playlist reshuffles (`HomeArrival`). Turning detection off stops the OnePlus service first, then sends `autoPause=false`; if Samsung is unreachable then it may still pause once.
- **Live dashboard** (`HomeDashboard`/`HomeDashboardCard`, top of Home on both phones): a pure projection rebuilt every second, never stored. Samsung: itself, the OnePlus as online while an authenticated request arrived within 90 s (`RemoteServerService.onePlus`, memory only, reset with the listener), the song, breaks, and the OnePlus as home while seen (request, check-in or beacon) within the 5-min pause window, away only if it has checked in with detection on, otherwise unknown. OnePlus: Samsung online = the status poll is connected; home = PresenceService's verdict when detection runs, else home while connected to Samsung, else unknown.
- **PresenceViewModel / PresenceSection**: settings, permission and battery-optimization projection; `HomeDjActivity` owns the permission launchers (foreground permissions, then "Allow all the time").

## Operational limits

Playback capture is limited to permitted USAGE_MEDIA/GAME/UNKNOWN sources on OnePlus. DRM, privacy-restricted apps and calls cannot be captured. MediaProjection must be granted from a visible Activity and runs under the mediaProjection foreground-service type; its one-shot consent cannot be reused after stop. Live audio needs both phones on a stable private Wi-Fi network; buffering adds intentional latency and does not imply lip-sync or gapless guarantees.

Account metadata is **not** the media source. Google OAuth used for playlist discovery is not supplied to NewPipe; private content, DRM and subscription streams are not unlocked. Audio is directly downloaded only if an unprotected format is exposed by the independent extractor. No third-party stream URLs, account cookies or OAuth values are logged or stored. Shared `Music/HomeDJ` files from earlier Termux versions remain available via MediaStore with Android media-read permission.

Automatic library refresh/worker execution can be deferred or interrupted by Android/One UI; playing already downloaded local audio is independent of connectivity. Paired browsing reads cached metadata only; Google authorization/refresh still happens on Samsung. Remote playlists queue at most 2,000 cached tracks. Connection loss does not interrupt Samsung playback. Media queues aren't restored after process death. The native download queue is idempotent per video ID, but a failed manual download gets one automatic Wi-Fi retry on the hourly sync; after that (or after the extractor changes) a user may need to retry it.

The NewPipe Extractor dependency is GPL-3.0-or-later. Its source is not copied; GPL obligations apply to redistribution. No Room schema or migrations.

The opt-in foreground LAN listener returns START_STICKY so Android can try to restore it after process death; role and enabled preferences still gate incoming commands. While enabled it holds a non-reference-counted `WIFI_MODE_FULL_HIGH_PERF` Wi-Fi lock so screen-off Wi-Fi power save does not drop inbound connections (Android 14+ downgrades this to screen-on only). The Controller ViewModel owns one short-lived request/response poll loop while the Controller UI is started (`LifecycleStartEffect`), polls every three seconds when healthy, and applies capped 1–30-second backoff when unreachable. Returning to the app, Wi-Fi availability, or a failed command re-polls immediately through a conflated refresh signal instead of restarting the loop. One missed poll on a confirmed link is tolerated; the second marks it disconnected. Command transport failures are unknown outcomes: they show an error and trigger a status re-read rather than marking the link down. A peer change resets browser state; reconnection to the same peer retains cached sections and checks the existing revision fields and reuses the current section while unchanged. Manual paired private IPv4 remains the address source (no mDNS/parallel transport); only Samsung owns playback. Force-stop and OEM background restrictions can still prevent execution. The disposable browsing cache above adds no change to existing persisted or wire schemas.

## Enforcement

`HomeDjGuardrailTest` (JVM) bans `GlobalScope`, `runBlocking`, `Thread.sleep`, `!!`, raw `collectAsState(` and destructive migration in production Kotlin; keeps `allowBackup`/cleartext off and exported components limited to `HomeDjActivity` and `PlaybackService`; and keeps the agent skill/instruction mirrors identical, parseable and free of foreign-project references.

## Music schedule and queue

- **ScheduleStore** (`music_schedule.json`) is the only truth for weekly slots; only the Samsung `ScheduleViewModel` writes it, validated by `SchedulePolicy` (selected ISO weekdays, minute-resolution start < end ≤ 24:00, no overlap on shared days, 1–10 playlist IDs, volume 0–100) and atomically replaced. Version 1 reads as daily whole-hour slots; weekly/minute writes use version 2 with explicit days and minutes, preventing old builds from treating weekly slots as daily. All-daily whole-hour schedules keep writing version 1. The existing filename, size bound and slot identities remain unchanged; downgrade editing is unsupported.
- **ScheduleSlotEditor** is shared by the Schedule tab and Samsung's playlist top-menu "Add to schedule" shortcut. The shortcut preselects the open playlist. Draft days, times, volume and playlist IDs use restorable Compose state; save is first-wins in `ScheduleViewModel`, checks Server role and closes only after commit. Failed/overlapping edits keep the draft open. A read begun before a successful save cannot overwrite the committed slot projection. Scheduling remains Samsung-only, with no LAN additions; alarm permission requests still belong to `HomeDjActivity`.
- **MusicScheduler** lives inside PlaybackService and is the only code that applies the schedule to the session player. It acts on three triggers: a boundary tick (exact alarm, schedule edit, boot/clock change via a near alarm), queue end, and "Resume schedule". It re-checks the Server role, reads the stores, then decides and mutates the player without suspending, so no other queue change interleaves; it also re-arms the single next-boundary alarm. Scheduled queues tag every item with a per-day slot key (`homedj_slot`); anything without it is a person's queue (Samsung UI, LAN `playTrack`/`playPlaylist`). A person's queue that is still playing finishes first and its end starts the active slot; a slot end pauses only scheduled music; a live cast (`LiveAudioSink.active`) blocks scheduled starts. Its fourth command, `PLAY_SCENE` (own UID only), plays a light scene's linked playlists shuffled: `Lights.applySceneLocked`, after the scene's lights were sent and still under the Lights mutex, hands the scene ID and playlist IDs to it through `ScenePlayback` (a short-lived `MediaController` on Main, released in `finally`, reply awaited ≤5 s; a timeout is reported as an unknown outcome). It re-checks the role, refuses while casting, replaces any queue (a person's or scheduled) and tags items `homedj_scene` = scene ID + playlist IDs, so re-applying the same scene while its queue is unfinished only resumes it. A scene queue has no slot key, so the schedule treats it as a person's queue. The music outcome is appended to the scene's outcome text (history, activity feed); the lights' result alone decides `ok`.
- **ScheduleAlarmReceiver** (not exported) only delivers boundaries to PlaybackService via a MediaController custom command; exact alarms are what allow the media-playback FGS to start from the background. Boot/package-replaced/clock/permission broadcasts arm a 3-second alarm instead of playing directly (Android 15 forbids mediaPlayback FGS from BOOT_COMPLETED).
- Every new queue starts with shuffle on (`onSetMediaItems`); the shuffle button still turns it off for that queue. "Play next" is an own-UID session command so the service can place the song right after the current one in the shuffled order; "Add to queue" appends through the controller. The Samsung UI projects the up-next list from the controller timeline in play order.
- Limits: schedule changes made while a slot is active take effect on save (a tick runs). Boundaries search selected weekdays through the following week, including the preceding day's 24:00 end; times follow the server's local zone and existing daylight-saving resolution. Slots play only cached playlist tracks, so Library must have synced them. Exact alarms can be denied or delayed by Samsung battery restrictions. Two-phone and device behavior is not verified by JVM tests.

## Music breaks

- **MusicBreakStore** (SharedPreferences `homedj_music_breaks`, key `settings` = `MusicBreakSettings` JSON) on Samsung is the only truth for break settings. It is off by default and validated by `MusicBreakSettings.isValid`. The Samsung UI writes it through `ServerPlaybackViewModel`, and the OnePlus writes it through the LAN `setBreaks` command. The same JSON goes over the wire in every status reply (`breaks`) with `breakSeconds` (0 = no break), and both fields are optional for older builds.
- **MusicBreaks** lives inside PlaybackService and only pauses/resumes the session, delegating its configured resume fade to PlaybackPlayer. It never changes the queue. Music time counts only while the player is actually playing. When a random session expires, it arms ExoPlayer's `pauseAtEndOfMediaItems` and lets the current song finish, with PlaybackPlayer fading its final 5 seconds. The `END_OF_MEDIA_ITEM` play-when-ready callback starts the full random silence (with a chance of a long one); it clears the song-end pause so playback can continue with the next queued song after the break, with a fade-in. Buffering does not restart an armed music interval. Manual play/pause, disabling breaks and schedule restart/cancel clear a pending song-end pause. Durations use `elapsedRealtime`. A partial wake lock with a timeout keeps the silence timer accurate with the screen off. `onUpdateNotification` keeps the media FGS during a break, because Media3 drops foreground at most 10 minutes after a pause and a later resume could then be refused from the background.
- **User intent wins:** the session player is `UserCommandPlayer` (a ForwardingPlayer), so every play/pause from the Samsung UI, the LAN, the notification or a media button reaches MusicBreaks: Play ends a break, Pause cancels its resume, and starting a cast stops both decks immediately (retaining queue/position) and cancels its resume. Turning breaks off or leaving Server mode during a break leaves music paused. A manual change while music plays (next/previous, a picked song or playlist) never re-rolls the music clock: the crossfade's incoming deck inherits a break due after the current song, and a Play while music already plays (the one that follows a picked song) does not cancel it.
- **With the schedule:** a slot end (`ScheduleAction.Pause`) cancels a break, and a slot start (`Start`) restarts the music clock. A break resume re-checks that nothing is casting and that a scheduled queue's slot instance is still active (`MusicScheduler.queueMayPlayNow`). A person's queue on a break counts as playing, so it still finishes before a slot starts.
- **Next break**: MusicBreaks publishes `MusicBreaks.nextBreak` (music left, counting only while playing, 0 = once the current song ends, null while off, on a break or before the first song) next to `resumeAt`. Both are projections of the scheduler, read by Samsung's dashboard and sent in every status reply as optional `nextBreakSeconds`; the OnePlus counts it down between polls only while Samsung plays and never to zero on its own.
- Limits: settings changes apply from the next music session. Break state is in memory and is lost with the process. Fade/foreground/wake-lock behavior on the Samsung is not verified by JVM tests.

## Playback transitions

- **PlaybackPlayer / PlaybackFades** are collaborators owned and released by PlaybackService, with two bounded decks and the existing single MediaLibrarySession. The active deck alone supplies queue/playback truth to MusicScheduler, MusicBreaks, PlaybackRecovery and both phones. The other deck is either a silent preparation of the next song or an outgoing tail; it cannot accept independent commands. Decks share the existing thread-safe resolver and stable ID URIs. This is the explicit exception to the former single-ExoPlayer rule for true overlapping crossfade; no Controller player or second session is created.
- Manual song/queue changes overlap for 3 seconds; automatic song transitions overlap for up to 4 seconds. Both use equal-power sine/cosine gains with angle timing blended from 75% linear progression and 25% smoothstep: lightly eased ends with an incoming song that becomes audible promptly. Automatic preparation begins within 20 seconds of a known end, preserves the current shuffle order, and starts the overlap only if the next deck is ready. Queue/shuffle/repeat edits invalidate preparation. A pending music break blocks automatic overlap and fades the final 5 seconds while Media3 still decides the song's natural end. Failed preparation falls back to normal Media3 progression; a manual replacement's outgoing tail is bounded to 15 seconds of loading before normal recovery owns the incoming error.
- Manual and scheduled play/pause use 5-second smooth envelopes; a break resume uses the existing configured fade duration. Pause intent is reflected immediately in session state while the audible tail fades. Play reverses a pending pause from its present gain. Rapid song changes cancel obsolete envelopes and reuse the spare for the newest intent; no third deck or unbounded command queue exists. Seeking inside a song remains a seek. Role changes, cast start, focus loss and unplugging headphones silence both decks immediately and cancel obsolete envelopes. Break timers are cancelled on safety interruptions. Transient focus loss may resume only if playback was still requested and no later pause/stop intervened.
- One service-owned AudioFocusRequest covers both decks (neither ExoPlayer requests its own); Android applies media ducking to the app's players. The noisy receiver uses the existing AndroidX Core API and unregisters at release. Preload polling runs only while playback is active; animation jobs and the poll belong to the service's Main scope and end with it. - **LoudnessNormalizer / LoudnessLeveler**: each deck's `DefaultAudioSink` (built by `normalizedRenderers`, wrapped in the pass-through `PulseAudioSink` for the light show) runs its own 16-bit PCM processor ahead of Media3's speed/silence processors, so streamed and downloaded songs play near -14 LUFS. NewPipe and downloaded files carry no YouTube loudness value, so it measures BS.1770 K-weighted, gated loudness while playing (running average from the song start, then a ~30 s window), moves gain at most 1 dB per 100 ms down and 0.3 dB up within -12/+10 dB, and a peak guard stops boosted audio clipping. No look-ahead or latency, so fade timing and `Player.volume` (applied after it) are unchanged. State lives only in the deck's playback thread: a flush (seek/format change) re-measures from the present gain, a stopped deck starts from unity. Always on; no setting, persisted key or LAN field. Live casts (`LiveAudioSink`) are not normalized. Audible behavior on the Samsung needs device verification.

- **Download recovery and live projection**: PlaylistDownloads serializes setup with cancellation and top-up, commits the existing playlist intent before enqueue, and uses OfflineAudioLibrary.savedIds for one directory snapshot per selection. YouTubeViewModel.showSavedCatalog requests the existing unique top-up on reopening; WorkManager restores already queued songs and each transfer rechecks for an existing file before resolving a stream. Completed audio and details publish a revision before thumbnail networking. The Controller records songsDownloadsRevision only when rows are loaded/refreshed; status replies can advance downloadsRevision without consuming a pending row refresh, including while browsing is loading. Both playlist headers render downloaded/downloading counts. Existing persisted names, data formats, four-transfer concurrency, role gates, failure skips and LAN fields remain unchanged.
