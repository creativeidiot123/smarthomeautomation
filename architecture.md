# HomeDJ architecture

## Owners and truth

- **ModeStore**: Preferences DataStore stores the device-local Server/Controller role.
- **PlaybackService**: one Media3 MediaLibraryService/ExoPlayer is the sole playback/queue owner, foreground only during supported media playback; observes the role to stop outside Server mode. `PlaybackRecovery` (Metrolist-style) keeps one failed track from halting the queue: network loss retries after 3/6/12 s, a CDN-rejected signed link is invalidated and retried once, anything else skips; five consecutive skips or the queue end stop playback.
- **ServerPlaybackViewModel**: client projection and commands to the same Media3 session, never another player. Android document-picker URIs are persisted when the user selects external audio.
- **RemoteServerService / RemoteChannel / RemotePrefs / RemoteControllerViewModel**: opt-in AES-GCM authenticated private-LAN protocol. The paired controller pages through server-owned playlists/tracks/downloads and sends verified track/playlist/download commands; it never accesses local audio or Google OAuth tokens directly. RemoteLibraryCommands validates catalog membership before Media3 mutation or WorkManager enqueue. `importPlaylist` sends only a link; Samsung parses it with YouTubePlaylistLinks, reads it through NativeAudioSource, re-checks the Server role and commits via SavedPlaylistStore. That reply can take seconds, so the controller sends it outside its command mutex with a longer read timeout and treats a timeout as an unknown outcome.
- **YouTubePlaylistRepository**: read-only Google YouTube Data API for owned/imported playlists, pagination and titles. Authentication token lives only in YouTubeViewModel, not in storage.
- **SavedPlaylistStore**: 4-MB atomic app-private JSON for account-scoped YouTube metadata; serializes screen/Worker writes in-process, erases metadata on explicit disconnect. Public links read without a token join the current snapshot as imported playlists; connecting a different account still replaces the snapshot.
- **NativeAudioSource / HomeDjMediaResolver**: NewPipe Extractor v0.26.5 with an application-owned HTTPS Downloader; Media3's ResolvingDataSource resolves stable internal video-ID URIs at load-time (prefer local file, else public non-DRM progressive audio) and caches transient signed links for at most four minutes per player-service instance; a YouTube refusal is cached for the same time so Media3 load retries do not re-query. Requests mirror NewPipe: the extractor Downloader sends NewPipe's desktop browser agent (extractor headers override; its consent cookie is forwarded, HTTP 429 maps to ReCaptchaException) and stream requests use NewPipe's YoutubeHttpDataSource shape (POST body, `rn` counter, visionOS or browser agent, web CORS headers). With no PoToken provider installed, visionOS-client links are preferred because ANDROID-client links can need one. It also reads public/unlisted playlists by ID (PlaylistInfo, bounded to 500 songs and 8 pages) when no OAuth token is available. The extractor is initialized once, network reads run on Dispatchers.IO, extraction response bodies are size-bounded. Only HTTPS GoogleVideo audio URLs are accepted; no signed URLs are persisted.
- **OfflineAudioLibrary**: owner of app-private files in `files/offline_audio`, keyed by validated 11-character video IDs. WorkManager uses one unique job per ID for manual saves and a separate one for automatic playlist saves (so a withdrawn auto opt-in never swallows a manual save), each with its own atomic `.part` -> final file rename, at most three transfers at once in the process (WorkManager starts every queued save together, and unbounded blocking transfers starved the shared IO pool that DataStore needs, freezing the UI at start-up), a 100-MiB per-track and 2-GiB aggregate limit (kept partials count toward it). `AudioTransfer` fetches 512-KiB Range requests (NewPipe downloader style) that must stay on the GoogleVideo CDN after redirects; a transient failure keeps the itag-keyed partial so the next attempt resumes it, while a rejection (consent, budget, range mismatch) or final failure deletes it. Completed files are durable. Each save request carries tags `homedj_offline` and `homedj_offline_id_<videoId>`; `pendingIds` reads queued/running saves from WorkManager (a projection) for live "Saving…" rows on both phones, while the committed file stays the "Saved" truth. Work queued before tags existed is not listed as saving until it finishes.
- **Playlist play**: tapping a song in a playlist (Samsung Library, or LAN `playTrack` with the optional `playlist` field) queues that playlist from the song via `playlistQueue` (≤500 songs, always including the tapped one); `UserCommandPlayer` starts the shuffle order at the tapped song and re-prepares an errored player on skip. LAN `tracks` items carry an optional `saving` flag; the controller re-reads only rows still saving on each poll. Older builds ignore both fields.
- **OfflineAudioWorker**: non-interactive, cancelable, idempotent per-song download. Checks Server role before and throughout the transfer, optional account key/playlist opt-in for automatic downloads, and network/space/size constraints; automated jobs require unmetered connection, manual jobs allow connected; reports failures by safe type and video ID, never signed URLs.
- **AutoLibraryConfig / AutoLibraryWorker**: opt-in device-local settings and unique inexact 12-hour WorkManager job (unmetered + battery-not-low). Silent Google OAuth and account checks precede metadata updates, followed by downloading up to 150 selected tracks through the same native offline WorkManager queue. No Termux command or other-process service lifetime.
- **LiveAudioCastService / LiveAudioSink**: user-consented MediaProjection and AudioRecord playback capture on Controller sends fixed 48-kHz stereo 16-bit PCM packets (20 ms) through the existing authenticated AES-GCM TCP session; Samsung's RemoteServerService accepts one live cast, pauses Media3, and feeds an AudioTrack with focus that starts after 200 ms of audio is queued and drops packets only while 400 ms is already queued, so Wi-Fi jitter is absorbed but latency cannot grow after a stall; the OnePlus keeps 500 ms of capture buffer so a stall loses no audio. Each PCM frame's AES-GCM AAD includes its sequence number, so replayed, dropped or reordered frames end the cast (both phones need the same build). Multiple short-lived remote sessions are handled concurrently with a six-connection semaphore. Live PCM is never persisted. Stopping the service, permission revocation, remote playback or network interruption closes the live socket and releases the capture/sink. No additional publicly exposed listener or pairing secret.
- **RemoteActivity** (process `object`, Samsung): in-memory, newest-first feed (30 entries) of changes made from either phone (OnePlus commands recorded by `RemoteServerService.handle` after they apply; Samsung UI actions by its ViewModels, custom session commands only on success). Display only, never a command queue; lost with the process; titles only, never links/tokens/addresses, not logged. Samsung shows it as the Activity card, and every status reply carries the newest 8 as optional `activity` (age in seconds, so phone clocks may differ) for the OnePlus card. Race protection: the OnePlus sends the state it showed (`playPause.play`, `shuffle.on`, `next/previous.index`), so Samsung applies intent instead of toggling stale state and refuses a skip of a song it already left; older builds ignore these fields and toggle. `SavedPlaylistStore.revision` (bumped per commit, wall-clock seeded) reloads Samsung's Library screen and is sent as optional `library` so the OnePlus re-reads its playlist list.
- **HomeDjActivity / YouTubeSection / YouTubeViewModel**: user actions, UI state and read-only projections. On-demand stream resolves are Activity-lifecycle-bound; durable downloads belong to WorkManager rather than the UI lifecycle.
- **HomeDjScreens / RemoteUiSection / YouTubeSection**: Material 3 Expressive presentation groups each role into Home, Library and Setup behind a bottom navigation bar. Tab choice and playlist-view navigation are restorable Compose-only UI state; remote and playback truth continue to come exclusively from their ViewModels/services. Pairing codes are masked until revealed in Setup. Wallpaper-based Material You colors apply where Android supports dynamic color.
- **PlayerUi / MusicListItems / MusicArtwork** (stateless Compose): `MusicShell` hosts the mini player and the full-screen player (open/closed is `rememberSaveable`; system back, the chevron, or a downward drag closes it; it closes when the queue ends). Both render `NowPlayingUi`, a per-role projection of `ServerPlaybackUiState` (Samsung) or `RemoteUiState` (OnePlus), and send the same controller/LAN commands as before. Song menus are `ModalBottomSheet`s keyed by a saveable song ID. Artwork: `youTubeArtworkUrl` derives an `i.ytimg.com` URL from a validated video ID; the item builders (`ServerPlaybackViewModel`, `MusicScheduler`, `RemoteLibraryCommands`) set it as Media3 `artworkUri`, so the session notification also gets art and the Samsung UI reads it back from the controller timeline. Coil's singleton image loader owns the discardable memory/disk image cache (key = URL, HTTP freshness, evicted by size, under `cacheDir`); it holds only public thumbnails and is not cleared on YouTube disconnect.

## Operational limits

Playback capture is limited to permitted USAGE_MEDIA/GAME/UNKNOWN sources on OnePlus. DRM, privacy-restricted apps and calls cannot be captured. MediaProjection must be granted from a visible Activity and runs under the mediaProjection foreground-service type; its one-shot consent cannot be reused after stop. Live audio needs both phones on a stable private Wi-Fi network; buffering adds intentional latency and does not imply lip-sync or gapless guarantees.

Account metadata is **not** the media source. Google OAuth used for playlist discovery is not supplied to NewPipe; private content, DRM and subscription streams are not unlocked. Audio is directly downloaded only if an unprotected format is exposed by the independent extractor. No third-party stream URLs, account cookies or OAuth values are logged or stored. Shared `Music/HomeDJ` files from earlier Termux versions remain available via MediaStore with Android media-read permission.

Automatic library refresh/worker execution can be deferred or interrupted by Android/One UI; playing already downloaded local audio is independent of connectivity. Paired browsing reads cached metadata only; Google authorization/refresh still happens on Samsung. Remote playlists queue at most 500 cached tracks. Connection loss does not interrupt Samsung playback. Media queues aren't restored after process death. The native download queue is idempotent per video ID, but a user may need to retry a failed download after the extractor changes.

The NewPipe Extractor dependency is GPL-3.0-or-later. Its source is not copied; GPL obligations apply to redistribution. No Room schema or migrations.

The opt-in foreground LAN listener returns START_STICKY so Android can try to restore it after process death; role and enabled preferences still gate incoming commands. While enabled it holds a non-reference-counted `WIFI_MODE_FULL_HIGH_PERF` Wi-Fi lock so screen-off Wi-Fi power save does not drop inbound connections (Android 14+ downgrades this to screen-on only). The Controller ViewModel owns one short-lived request/response poll loop while the Controller UI is started (`LifecycleStartEffect`), polls every three seconds when healthy, and applies capped 1–30-second backoff when unreachable. Returning to the app, Wi-Fi availability, or a failed command re-polls immediately through a conflated refresh signal instead of restarting the loop. One missed poll on a confirmed link is tolerated; the second marks it disconnected. Command transport failures are unknown outcomes: they show an error and trigger a status re-read rather than marking the link down. A peer change resets browser state; reconnection to the same peer keeps loaded library pages and re-fetches only an empty or interrupted section. Manual paired private IPv4 remains the address source (no mDNS/parallel transport); only Samsung owns playback. Force-stop and OEM background restrictions can still prevent execution. No persistence/schema change.

## Enforcement

`HomeDjGuardrailTest` (JVM) bans `GlobalScope`, `runBlocking`, `Thread.sleep`, `!!`, raw `collectAsState(` and destructive migration in production Kotlin; keeps `allowBackup`/cleartext off and exported components limited to `HomeDjActivity` and `PlaybackService`; and keeps the agent skill/instruction mirrors identical, parseable and free of foreign-project references.

## Music schedule and queue

- **ScheduleStore** (`music_schedule.json`) is the only truth for daily slots; only the Samsung `ScheduleViewModel` writes it, validated by `SchedulePolicy` (no overlap, start < end ≤ 24, 1–10 playlist IDs, volume 0–100) and atomically replaced.
- **MusicScheduler** lives inside PlaybackService and is the only code that applies the schedule to the sole player. It acts on three triggers: a boundary tick (exact alarm, schedule edit, boot/clock change via a near alarm), queue end, and "Resume schedule". It re-checks the Server role, reads the stores, then decides and mutates the player without suspending, so no other queue change interleaves; it also re-arms the single next-boundary alarm. Scheduled queues tag every item with a per-day slot key (`homedj_slot`); anything without it is a person's queue (Samsung UI, LAN `playTrack`/`playPlaylist`). A person's queue that is still playing finishes first and its end starts the active slot; a slot end pauses only scheduled music; a live cast (`LiveAudioSink.active`) blocks scheduled starts.
- **ScheduleAlarmReceiver** (not exported) only delivers boundaries to PlaybackService via a MediaController custom command; exact alarms are what allow the media-playback FGS to start from the background. Boot/package-replaced/clock/permission broadcasts arm a 3-second alarm instead of playing directly (Android 15 forbids mediaPlayback FGS from BOOT_COMPLETED).
- Every new queue starts with shuffle on (`onSetMediaItems`); the shuffle button still turns it off for that queue. "Play next" is an own-UID session command so the service can place the song right after the current one in the shuffled order; "Add to queue" appends through the controller. The Samsung UI projects the up-next list from the controller timeline in play order.
- Limits: schedule changes made while a slot is active take effect on save (a tick runs). Slots play only cached playlist tracks, so Library must have synced them. Exact alarms can be denied or delayed by Samsung battery restrictions. Two-phone and device behavior is not verified by JVM tests.

## Music breaks

- **MusicBreakStore** (SharedPreferences `homedj_music_breaks`, key `settings` = `MusicBreakSettings` JSON) on Samsung is the only truth for break settings. It is off by default and validated by `MusicBreakSettings.isValid`. The Samsung UI writes it through `ServerPlaybackViewModel`, and the OnePlus writes it through the LAN `setBreaks` command. The same JSON goes over the wire in every status reply (`breaks`) with `breakSeconds` (0 = no break), and both fields are optional for older builds.
- **MusicBreaks** lives inside PlaybackService and only fades (`player.volume`, squared gain), pauses and resumes the sole player. It never changes the queue. Music time counts only while the player is actually playing. When a random session ends, it fades out, pauses for a random silence (with a chance of a long one), then fades back in. Durations use `elapsedRealtime`. A partial wake lock with a timeout keeps the silence timer accurate with the screen off. `onUpdateNotification` keeps the media FGS during a break, because Media3 drops foreground at most 10 minutes after a pause and a later resume could then be refused from the background.
- **User intent wins:** the session player is `UserCommandPlayer` (a ForwardingPlayer), so every play/pause from the Samsung UI, the LAN, the notification or a media button reaches MusicBreaks: Play ends a break, Pause cancels its resume, and starting a cast pauses and so cancels it. Turning breaks off or leaving Server mode during a break leaves music paused.
- **With the schedule:** a slot end (`ScheduleAction.Pause`) cancels a break, and a slot start (`Start`) restarts the music clock. A break resume re-checks that nothing is casting and that a scheduled queue's slot instance is still active (`MusicScheduler.queueMayPlayNow`). A person's queue on a break counts as playing, so it still finishes before a slot starts.
- Limits: settings changes apply from the next music session. Break state is in memory and is lost with the process. Fade/foreground/wake-lock behavior on the Samsung is not verified by JVM tests.
